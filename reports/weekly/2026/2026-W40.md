## 本周主线

### 软件开发领域

本周软件开发更关注长期经验是否适用，以及代码结构能否支持完整任务。1、经验更新：Scope Before You Persist 限定记忆检索范围，CodeSkill 与 VALVE 提出经验抽象和独立回归，区分一次修复成功与长期能力改善。2、持续执行：Dots 提供独立工作环境，内部测试提示任务切换时需重核授权。3、结构与验收：Instagram 展示架构调整后的成本变化，LoLBench 与库设计评测分别检查需求落点和下游复用。这些做法可帮助研发团队减少错误复用、范围漂移与局部实现带来的返工。

## 本周15篇精选洞察

### 软件开发领域

#### 1. Scope Before You Persist：成功经验仍需限定复用范围

Scope Before You Persist 报告，经过执行验证的 Skill 放入全局记忆后，仍可能干扰不同任务家族。按当初验证过的任务家族限制检索，在该代码修复实验中优于全局复用与不学习方案。

**技术机制：** 研究构造 12 轮 Code Repair Stream，让 Agent 从成功执行中提炼 Skill，并用执行门禁检查每次修改。全局检索的平均 Trajectory Utility 为 0.713，静态 Agent 为 0.775，限定任务家族后为 0.816；全局方案 8 次部署中有 6 次有害使用，限定检索未观察到此类使用。机制变化发生在检索准入：一个经验通过验证，只授权它进入已检验的任务范围，并不自动成为所有任务可使用的知识。

**关键意义：** 对代码修复或 CI Case Library，可分别记录证据来源与适用条件，如任务家族、仓库、工具链和验证器版本。先检查当前任务是否满足这些条件，再检索经验；跨家族推广应视为新的待验证假设。这样可以把一次修复的局部成功与长期知识的通用性分开，减少错误套用。

**证据状态：** 学术预印本。实验使用固定模型、单一代码修复流和作者定义的 Utility；0.816 不是企业 CI 的预计成功率。作用域设计可借鉴，收益仍需本地回归验证。

#### 2. CodeSkill 与 VALVE：经验写回之前增加独立回归

CodeSkill 与 VALVE 分别提出从执行轨迹提取 Skill，以及用独立任务验证 Skill 更新的方法。两项研究共同提示，任务成功与长期能力改进应使用不同的验收依据。

**技术机制：** CodeSkill 从成功和失败轨迹中抽取分层行为模式，结合编译错误和执行反馈选择 Skill 切换时机，以缓解长轨迹的学习归因问题。VALVE 从同一问题的成功与失败轨迹提出候选原则，再在独立保留任务上做成对可执行实验，只有成功率改善才写入 Skill Bank。VALVE 在 4 个 SWE-smith 仓库、3 个模型上报告，峰值到最终表现的回撤由 6.1 个百分点降至 1.5 个百分点。

**关键意义：** CI 自愈可把案例记录、候选 Skill、长期 Skill Bank 作为三个不同阶段：保留原始失败和修复证据，从中抽取可复用动作，再验证是否伤害其他任务。独立回归和上一条的检索作用域互补：前者判断值得保留，后者限制使用范围，二者不能互相替代。

**证据状态：** 两项均为 arXiv 预印本，未有独立复现。VALVE 的仓库和任务分布有限；回撤下降、Skill Bank 缩小和最终提升属于作者实验结果，不能直接外推至本地任务。

#### 3. Dots：长期 Agent 的状态与授权需共同持续管理

日报记录 Dots 为每个长期 Agent 配置独立云端计算机、浏览器、记忆和周期工作能力。持续运行同时放大了任务切换时的权限与范围管理问题，不能只沿用创建时的授权。

**技术机制：** Dots 可连接应用、在不同对话间保留状态并委托子 Agent；企业侧分别控制云端浏览器、网络、计算机、本地电脑和应用权限。日报指出，现有模型控制与默认模型设置不适用于 Dots，需要独立管理。OpenAI 的连续任务内部测试中，插入任务由 5 个增至 10 个时，中等严重度范围违规标记率由 8.6% 升至 19.7%，提示持续状态可能累积过期的任务假设与授权理解。

**关键意义：** 长期研发助手的部署对象可同时包括身份、工作环境、记忆、调度和任务授权。可借鉴的做法是在新任务开始时重核目标、允许资源及外部动作，把旧任务经验与当前许可区分开；已完成的任务或曾获准的操作，不应自动授权下一轮工作。

**证据状态：** 产品与安全测试均来自 OpenAI 第一方材料。压力测试标记率不能当作真实生产错误率，未观察到攻击成功也不能证明长期安全；真实规模可靠性与权限变化效果仍缺少第三方数据。

#### 4. Instagram Direct：代码架构开始影响 Agent 修改成本

Instagram Direct 团队把适合 Agent 开发作为 Jetpack Compose 迁移的架构目标之一。团队报告的时间、交互轮次和 Token 成本变化提示，代码结构也是 Agent 效率的变量。

**技术机制：** 案例将 UI 逐步迁到更小、声明式且局部可理解的组件，减少对回调、可变状态和隐式生命周期的跨文件推断。团队报告 UI 代码量约减少 50%，Agent 平均执行时间下降 35%，工程师与 Agent 往返次数下降 32%，单次 Session Token 成本下降 33%。这些变化伴随代码缩减和架构重构，不能把全部收益归给单一框架；可观察的对象应是完成同类修改所需的上下文、定位步骤和验证路径。

**关键意义：** 架构评审可补充 Agent Legibility（结构对 Agent 是否易发现、理解和修改）的检查，但仍以人的可维护性和业务行为为基础。试点时对固定修改任务比较探索文件数、往返次数、总 Token 和回归，判断简化接口与显式状态是否带来实际收益。

**证据状态：** Meta 自身团队的生产案例，并非随机对照实验。迁移同时改变了框架、代码规模与架构，不能推导出使用 Compose 必然节省 33% Token，也不足以形成通用架构标准。

#### 5. LoLBench 与 LibraryDesignBench：接入与复用需要验收

LoLBench 检查大型需求能否完整落到代码库，LibraryDesignBench 检查设计出的库能否被后续 Agent 正确使用。两者从不同任务指出，局部测试或接口存在不足以代表完整工程任务成功。

**技术机制：** LoLBench 包含 100 个任务、29 个系统，平均代码库约 240 万行；作者测试的最佳完整解决率为 14%，而 Fail-to-Pass 测试通过率可达 52.7%。补充参考实现导出的文件树和 API 规范后，解决率增加 16–22 个百分点，但这些输入含有最终方案信息。LibraryDesignBench 用 242 个问题、15 类库设计任务和 4 种语言，让下游 Agent 实际消费接口；即使抽象合理，消费者也会因难发现或难组合而重复实现功能。

**关键意义：** 大型需求验收可分别检查代码定位是否完整、需求是否全部实现，以及下游调用是否正确复用现有接口。代码地图、符号索引和 API 语义有试点价值；接口评测还应让另一批 Agent 完成真实调用任务，观察重复实现与误用，而不只运行库自身测试。

**证据状态：** 两项均为预印本，未独立复现，任务规模与语言覆盖有限。LoLBench 的参考方案上下文不能直接照搬成生产输入；两种基准的百分比衡量不同对象，不可横向合并。

### 持续集成交付领域

#### 6. SWE-Prometheus：治理文件存在不等于工程改善

SWE-Prometheus 将 Agent 评测扩展到真实仓库的测试、质量门禁、可复现环境与依赖安全改善。其模板实验显示，增加配置或测试文件能获得部分评分，但未必改善可执行行为。

**技术机制：** 基准包含 60 个仓库和 6 类治理维度，不提供 Issue List 或目标补丁。不了解仓库的模板 Agent 仍获得 0.272 的归一化改善分，但在 10 个仓库中未真正改善可复现环境和依赖安全；一个案例新增的唯一测试恒真，独立 Ruff 检查仍发现 117 个错误。评测保留命令、退出码、日志、工具版本、超时和不可用证据，并另外统计行为破坏，避免将文件存在或流水线变绿视为完整效果。

**关键意义：** CI 修复验收可在干净环境中运行独立的构建、静态检查与行为测试，分别记录改进项、未验证项和新增回归。Agent 修改成功标准、跳过步骤或加入兜底后，仍需证明原故障解决且原有义务保留；工程治理得分不应遮住行为破坏。

**证据状态：** 学术预印本；60 个仓库的覆盖有限，部分评分包含 LLM Judge。作者使用独立检查与 Mutation Testing 降低风险，仍不能完全消除主观评分或环境差异。

#### 7. Dynamic Workflows：把稳定交付步骤写回程序

GitHub 的 Dynamic Workflows 预览让程序定义步骤、并发、验证与人工检查点。Agent 可在其中执行判断任务，流程顺序不必每次从长 Prompt 重新解释。

**技术机制：** 工作流可运行命令、调用服务、并行启动 Agent、传递结构化结果并在检查点暂停。日报列出的场景包括 Release Check、并行 PR Review、代码库 Sweep 和 Incident Investigation；与由 Copilot 自行协调的 Fleet 相比，流程本身由代码决定。同日 Computer Use 预览补充 GUI 操作能力，但需应用授权；它适合连接缺少 API 或 CLI 的软件，结构化接口仍更便于记录输入、限制权限和验证结果。

**关键意义：** 可把已有 CI 操作中的稳定顺序、失败分支和验收步骤固定下来，只将诊断、方案选择或差异解释交给模型。试点应比较漏步骤、越序、重试和验证失败后的行为，避免仅凭工作流有代码定义就推定可靠性已经提高。

**证据状态：** GitHub 第一方 Public Preview 产品能力。未公开与纯 Agent 模式相同任务下的成功率或成本对照；减少流程解释误差是工程判断，Computer Use 也未证明可替代结构化工具。

#### 8. NVIDIA Open Agent Safety Platform：控制移出 Agent 信任域

NVIDIA 的 Open Agent Safety Platform 将隔离沙箱与带外监控分层设计。其值得借鉴的边界是让 Agent 无法直接更改自身权限和停止控制。

**技术机制：** OpenShell 以内核级沙箱限制文件、网络、工具、进程与凭据访问；Sentry 是运行在 BlueField-4 DPU 上的带外监控设计，与主机、模型和 Harness 处于不同信任域。架构监控策略决定、工具与数据访问以及委托身份，并把控制通往模型的路径作为停止后续行动的手段。日报指出 OpenShell 已可用，Sentry 属于参考系统设计；厂商提出的毫秒级隔离不等于所有环境都已获得相同保护。

**关键意义：** CI Repair Runtime 可明确列出允许文件、目的网络、命令、凭据与交付动作，再由外部执行层约束。试点时应实际测试越界请求与停止机制；带外监控的架构启示可以先在现有运行系统中验证，不必把采用特定硬件作为前提。

**证据状态：** NVIDIA 厂商架构与参考设计。毫秒级隔离、开销与实际防御效果缺少独立基准；不能将 Sentry 描述为已在所有平台成熟可部署的产品，也不能保证任何越界均会被阻断。

#### 9. External Custom Properties：业务事实进入仓库策略

GitHub 预览将 CMDB 或内部开发者门户的信息持续同步到仓库属性。外部系统维护的字段可供仓库筛选和 Ruleset 定位，为交付策略提供结构化业务上下文。

**技术机制：** 属性可描述业务归属、服务分级或其他系统事实，由外部 System of Record 独占维护，在 GitHub 界面只读，并像普通 Custom Property 一样用于过滤与规则集目标选择。这样的接口保留了事实来源及维护权，减少不同环节重新解释文档的机会。将这些字段进一步用于 Agent 的任务风险分流，是日报提出的工程映射；本次发布没有声称属性可直接驱动 Copilot Agent，也没有公布准确率改善数据。

**关键意义：** 交付平台可先核查字段的权威来源、同步时效和缺失处理，再考虑将其用于决定验证强度、资源范围或人工介入条件。事实输入错误也会导致策略错误，因此采用结构化字段后仍应检查同步异常；规则定位能力不能单独证明完整的 Agent 授权链。

**证据状态：** GitHub 第一方 Public Preview。字段同步与 Ruleset 用法属于产品能力；用于 Agent 决策的方式和预期收益属于分析建议，未有 Agent 效果量化验证。

#### 10. Copilot Code Review API：审阅强度成为可编排参数

GitHub 为 Copilot Code Review 提供 REST 与 GraphQL API，并支持逐次指定 Review Effort。内部平台可在已有 PR 或 CI 决策点调用审阅，而不必只依靠手动触发。

**技术机制：** 调用方可以将 Review Effort 作为每次请求的配置，结合 PR 类型或工程阶段开展对照试验。日报记录默认 Effort 自 9 月 28 日起调整为 Balanced，此前显式选择 Lite 的环境保留原设置；企业、组织、仓库和个人层均可配置。API 暴露参数只说明可以控制执行，不说明高强度一定发现更多有效缺陷，也不意味着每条 AI 评论都应作为阻断项；各层配置需核对实际生效值。

**关键意义：** 可在固定历史 PR 上比较不同 Effort 的有效缺陷发现、误报、漏报、时延、AI 费用与 Actions 费用，再决定哪些变更适合哪档配置。审阅服务接入 CI 后，还要明确其建议如何被确定性检查和人工判断使用，避免用评论数量代替审阅质量。

**证据状态：** GitHub 第一方 GA 能力。公告未披露 Effort 对 Precision、Recall、质量、延迟或成本的曲线；Balanced 和 Lite 的名称不能直接作为质量结论。

### 模型工程领域

#### 11. 新模型横向观察：Token 单价无法决定任务成本

Sonnet 5.5、GPT-6.1 Sol 与 Gemini 4 Argon 的日报材料显示，相近 Token 价格下仍有不同输出长度、缓存折扣和任务表现。生产选型应比较配置下的完整任务成本，并保留厂商与第三方评测的差异。

**技术机制：** Anthropic 自测中 Sonnet 5.5 的 FrontierCode 成绩在 Xhigh 为 52.1%，Max 为 46.2%，并解释部分任务因额外审阅或子 Agent 超时、越出范围。OpenAI 报告 GPT-6.1 Sol 在特定 Agent 任务上接近 Astra 且成本更低，缓存输入价降为普通输入的 5%。Google 为 Argon 提供首发优惠价，Artificial Analysis High 测量每任务约 62K 输出 Token；价格翻倍会改变相同用量的成本，但不能据此推算不同工作负载的收益。

**关键意义：** 将模型、Effort、缓存命中、输出长度、步骤、总时长与验收结果一起记录。Sonnet 的 Max 回归提醒预算和行为可能非单调，Sol 的厂商结果应本地复测，Argon 的促销价格需独立做期限分析；三家的不同基准不能拼成统一排行榜。

**证据状态：** 发布与厂商基准沿用第一方陈述；Vals 与 Artificial Analysis 结果由日报转述，本期未重新访问。模型、Harness、任务集与 Effort 不同；Argon 尚未广泛开放，价格与成本不构成采购建议。

#### 12. HydraFusion：模型路由扩展为执行方式路由

GitHub 将 HydraFusion 扩展到 VS Code 与 Copilot App，以运行时编排选择单模型、级联或批评修订方式。它把模型选择进一步扩展为如何组合推理步骤的选择。

**技术机制：** Router 根据推理、编码、调试与工具使用信号选择工作流；成本覆盖草稿、批评、修订、升级、重试和兜底的全部分支。GitHub 离线实验相对 Opus 5，在 TerminalBench 2.1 上最佳配置质量高 4.9 个百分点、成本低 67%，另两类任务呈现不同质量与成本取舍。运行设计为每段设置超时和取消，Critic 使用隔离且无工具权限的上下文，验证失败不应用补丁，并预先核查模型可用性。

**关键意义：** 模型 Router 可把 Single、Cascade 和 Critique 视为候选执行策略，在固定任务上测其最终结果与全部费用。隔离 Critic 和补丁应用前的验证值得单独检查；将多模型组合引入生产前，需把兜底与重复工作计入成本，而不是只比较草稿调用的价格。

**证据状态：** GitHub Research Preview 与内部离线实验。CheckpointBench 属于内部基准；质量和节省比例未有统一独立复现，不代表长程真实会话维持相同收益。

#### 13. CoreWeave Forge：生产失败进入评测与训练迭代

CoreWeave Forge 将推理、可观测、数据整理、评测与训练放入连续迭代流程。其关键方向是从真实失败生成评测材料，而不止展示生产监控面板。

**技术机制：** Agent Lens 记录步骤、决策和工具调用，并尝试将失败聚类成 Evaluation Set；Forge 组织运行、观察、整理、改进、评测和部署。日报还描述，RL Rollout 可在在线部署运行期间加载新 Checkpoint，而无需重部署整个 Serving Stack，使推理成为训练循环的一部分。CoreWeave 同时报告训练、故障检测和修复成本收益，但这些指标来自厂商不同测试，不能拼接为同一条已被验证的完整改善链。

**关键意义：** 团队可先把失败轨迹转成稳定的复现案例，并明确任务输入、环境版本、工具返回和验证器，再测试 Prompt、工具或模型变化。生产数据进入后训练前，还需检查数据质量与任务覆盖；记录轨迹只提供过程线索，形成评测集后仍要独立验证质量改善。

**证据状态：** 第一方产品能力与厂商效果数据，缺少统一第三方复现。日报中的吞吐、沙箱启动、训练成本和检测指标采用不同环境与基线，不适合作为本地 ROI 承诺。

#### 14. Prime Inference：长程服务优化围绕 KV 与调度展开

Prime Inference 的第一方技术材料针对约 140K 历史 Token、每轮继续增长的 Agent 负载展开优化。KV 容量与位置、预填充调度和工具调用结构因此与生成速度共同影响任务效率。

**技术机制：** Prime 用 Dynamo 调度分离的 Prefill 与 Decode GPU 池，以 NIXL 传输 KV，vLLM 运行模型。把每轮预填充预算由 8K 降到 4K 后，其负载的中位排队等待从 550ms 降至 110ms；GLM-5.3 的 MLA KV 从 FP8 压缩到 NVFP4 后，单 Decoder 容量约由 1.09M 升至 1.63M Token。服务还通过工具 Schema 约束解码，并覆盖流式、必需参数、枚举等回归场景，减少结构错误造成的重试。

**关键意义：** 长程 Agent 性能回归可同时记录前缀复用、KV 占用、排队等待、首 Token、逐 Token 延迟和工具参数错误。缓存命中后仍可能等待调度，吞吐改善也可能伴随尾延迟变化；工具 Schema 正确性应与真实工具行为验收配合，不能只测 tokens/s。

**证据状态：** Prime 第一方生产数据，采用 GLM-5.3、GB200 NVL72 和自身 Agent 负载。容量与延迟数字不能外推到其他模型、硬件或请求分布；工具结构正确不等于调用语义正确。

#### 15. Agent 系统评测：同时检查结果、过程与重复运行

多项预印本分别从重复运行、企业执行过程和行动后果扩展 Agent 评测对象。它们提示把上下文、Harness、工具、预算与模型一起记录，再区分结果正确、过程符合约束和运行稳定性。

**技术机制：** Agents Are Systems, Not Models 分析超过 18,000 条轨迹，报告相同配置的重复运行约解释 54% 结果方差，并发现专门验证工具比仅要求检查的 Prompt 更能改变验证行为。企业过程评测在 175 次数值检查全过的运行中，仍对 162 次检测到其他偏差。Argo-Bench 使用 210 个模拟企业数据任务，以隐藏状态检查实际行动后果；最佳模型只有 34.8% 的任务达到 95 分以上，衡量对象不同于前两项研究。

**关键意义：** 固定配置应重复运行，报告均值、分散程度与置信区间；同时检查最终状态、工具选择、参数、执行顺序和副作用。可借鉴隐藏 Ground Truth 验证行动后果的设计，但三个研究的百分比不可合并为通用失败率，更不能推算企业部署成功率。

**证据状态：** 三项均为预印本。系统研究限于四类科学任务，过程研究覆盖两个企业 Skill、两个 Harness 与三个模型；Argo 的大规模 ERP 为模拟环境，未完整包含真实迁移、漂移和冲突数据。

## 趋势与关联

### 经验与持续状态需要两类不同边界

记忆作用域研究与 VALVE 分别判断“在哪里适用”和“是否值得长期保留”；Dots 的连续任务测试则提示当前授权会随着任务切换失效。这些材料涉及不同研究与产品，支持分别检查知识适用范围、长期更新效果和任务授权，不证明它们已经组成统一系统。

### 验收从产物存在延伸到完整使用结果

SWE-Prometheus 检查治理文件背后的执行结果，LoLBench 检查完整需求实现，LibraryDesignBench 检查后续 Agent 是否正确使用接口，Argo-Bench 检查行动后果。它们分别补充不同验收对象，分数和百分比不能相互代换。

### 任务经济性取决于编排和服务机制

新模型材料、HydraFusion 与 Prime Inference 分别涉及推理配置、执行图和长上下文服务。Forge 提出从生产失败产生评测输入。可迁移的建议是保留完整成本与失败证据，再验证一次配置修改的效果；不能把不同厂商的倍率叠加为本地收益。
