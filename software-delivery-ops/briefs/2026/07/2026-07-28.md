## 今日主线

安全运营 Agent 正从单点分析助手走向闭环系统：攻击模拟、检测响应和系统修复分别由不同角色承担，再由共享上下文与执行边界连接。Microsoft Project Perception 给出了分层架构与首个漏洞管理场景，但能力仍处于 public preview 前夕，当前应重点验证闭环的权限、证据和人工接管条件。

#### 核心判断

Microsoft 公布 Project Perception，以红队代理寻找攻击路径、蓝队代理检测并响应、绿队代理修复系统配置，形成持续对抗与改进闭环。首个软件漏洞管理场景把专用安全模型接入多模型代理团队，展示了 SecOps Agent 从建议生成走向受控行动的分层设计。

#### 变化与技术机制

官方架构把系统拆成 signals、context、models、harness、agents 和 actuators：signals 接入安全遥测，context 组织资产与威胁背景，models 提供通用或专用推理能力，harness 负责编排与控制，agents 执行红蓝绿角色任务，actuators 才连接实际操作。首个场景使用 MAI-Cyber-1-Flash，并通过 MDASH 多模型 Agent 团队处理软件漏洞管理。

红队发现可利用路径后，蓝队验证检测与响应，绿队再把结论转化为系统修复或强化；新状态继续成为下一轮信号。这个循环的工程关键不是让单个 Agent 拥有更多工具，而是为不同职责设置独立证据、权限和停止条件，并由 harness 保留跨角色上下文与行动审批。

#### 关键解读

##### 角色分离把攻防冲突转化为可验证的控制关系

红、蓝、绿代理的目标不同，可以相互制造验证条件：攻击路径检验检测覆盖，响应结果检验攻击是否被阻断，修复结果再接受下一轮对抗。若每一步都保留证据与状态，这种闭环比单一“安全助手”更容易定位错误和评估效果。

##### Actuator 是自主性进入生产环境的真正边界

模型建议与系统变更之间必须经过明确执行接口。对高影响操作设置最小权限、审批、幂等键、回滚和紧急停止，才能避免推理错误直接扩散为生产副作用。

#### 证据与限制

Microsoft 官方文章确认架构、角色和首个场景，并称 Project Perception 计划于 2026-08-03 进入 public preview；当前尚无公开生产基准、误报与漏报数据、跨 Agent 冲突处理细节、人工审批粒度或修复回滚成功率，因此实际效果属于厂商主张。

#### 领域启示

**可借鉴。** 将安全 Agent 拆成发现、验证、响应和修复职责，用共享事件 ID 串联证据，并把实际写操作集中到可审计 actuator。

**适用条件。** 适用于具备稳定资产上下文、可回放安全遥测、分级工具权限和人工值守的漏洞管理或检测工程流程。

**不宜照搬。** 在缺少隔离演练环境、变更审批、回滚能力或责任边界时，不应让红队探索结果自动触发生产修复，也不能用厂商预览说明替代本地安全验证。
